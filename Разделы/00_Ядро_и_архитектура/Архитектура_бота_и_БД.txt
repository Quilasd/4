# ЯДРО БОТА И АРХИТЕКТУРА ПРОЕКТА

## 1. НАЗНАЧЕНИЕ

Этот раздел является техническим фундаментом проекта. Он описывает, на чём работает бот, как разделяется код, где хранятся данные и как обеспечивается изоляция миров.

Игровые правила из других разделов являются источником игровой логики. Этот раздел не переопределяет их, а задаёт техническую основу для реализации.

## 2. ОСНОВНОЙ СТЕК

Рекомендуемый основной стек:

- Python 3.12+;
- aiogram 3.x — Telegram Bot API и обработчики команд/кнопок;
- PostgreSQL — основная база данных;
- SQLAlchemy 2.x — ORM и работа с БД;
- Alembic — миграции схемы БД;
- asyncpg — асинхронный драйвер PostgreSQL;
- Pydantic 2.x — конфигурация и валидация данных;
- Redis — кэш, временные состояния, блокировки и очереди там, где это действительно необходимо;
- APScheduler либо собственный планировщик задач — игровые фоновые процессы;
- Docker Compose — локальная инфраструктура разработки.

SQLite не является основной БД проекта. Она допустима для небольших локальных тестов/прототипов, но рабочая многомировая система должна использовать PostgreSQL.

## 3. ПРИНЦИП МНОГОМИРОВОЙ СИСТЕМЫ

world_id является фундаментальным идентификатором игрового мира.

Практически каждая игровая сущность, относящаяся к конкретному миру, должна быть привязана к world_id напрямую или через однозначную связь.

Нельзя допускать смешивание данных разных миров.

Пример:

user_id → глобальный аккаунт игрока
user_id + world_id → персонаж/состояние игрока в конкретном мире

Один Telegram-пользователь может иметь разные персонажи в разных мирах.

## 6. WORLD CONTEXT

Каждый игровой запрос должен понимать, в каком мире он выполняется.

Контекст должен определяться до вызова игровой логики:

Telegram user → выбранный world_id → персонаж/административный контекст → действие.

Администратор с GLOBAL_ADMIN может переключать world_id без создания персонажа.

WORLD_ADMIN и MODERATOR работают только в разрешённых мирах.

## 7. ИГРОВОЕ ВРЕМЯ

Каждый мир хранит собственную игровую дату.

Единое правило проекта:

1 реальный день = 1 игровой месяц.

Переход игрового времени должен выполняться централизованным сервисом, а не отдельными обработчиками.

Изменение даты должно запускать необходимые фоновые процессы:
- старение;
- беременность;
- рождение детей;
- смерть от старости;
- события;
- экономические обновления;
- военные процессы;
- другие механики, привязанные к календарю.

## 8. СОБЫТИЙНАЯ СИСТЕМА

Игровые события не должны быть жёстко зашиты в Telegram-обработчики.

Рекомендуется единая система событий:

GameEvent
- id
- world_id
- type
- game_date
- source
- payload
- status

Это позволит запускать как автономные события мира, так и административные ивенты.

## 9. БЕЗОПАСНОСТЬ И ТРАНЗАКЦИИ

Критические игровые изменения должны выполняться в транзакциях PostgreSQL.

Особенно:
- смерть персонажа;
- рождение ребёнка;
- изменение наследника;
- передача территории;
- изменение казны;
- создание/расформирование армии;
- изучение магии;
- заключение брака;
- административные действия.

Для денежных и военных операций необходимо защищаться от двойного выполнения.

## 10. МИГРАЦИИ

Схема БД изменяется только через Alembic migrations.

Нельзя вручную изменять рабочую БД так, чтобы структура расходилась с миграциями.

Каждое изменение модели должно иметь соответствующую миграцию.

## 11. РЕПОЗИТОРИИ И СЕРВИСНЫЙ СЛОЙ

Игровая логика не должна напрямую выполнять SQL во всех обработчиках Telegram.

Рекомендуемая цепочка:

Telegram Handler → Service → Repository → PostgreSQL

Это позволит менять интерфейс бота, не переписывая игровую логику.

## 12. КЭШ И ВРЕМЕННЫЕ ДАННЫЕ

Redis используется только для данных, которые не являются единственным источником истины:
- FSM состояния;
- кэш часто читаемых данных;
- временные блокировки;
- очереди;
- rate limits.

Ключевые игровые данные всегда хранятся в PostgreSQL.

## 13. ЛОГИРОВАНИЕ И АУДИТ

Критические действия должны иметь аудит:
- кто выполнил действие;
- world_id;
- объект;
- действие;
- старое состояние;
- новое состояние;
- время.

Особенно важны административные действия и изменения экономики, армии, территории и персонажей.

## 14. ПРИНЦИП РАСШИРЕНИЯ

Новая игровая механика должна добавляться как отдельный модуль и связываться с существующими сервисами, а не ломать world_id, календарь, права и транзакционную модель.

Этот раздел является техническим фундаментом реализации проекта и может расширяться при появлении новых требований.
